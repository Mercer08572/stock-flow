# 仓库

仓库模块负责仓库主数据。

仓库是库存必需的逻辑维度。它描述库存可以存放在哪里，但不负责库存数量、库存层数量、预留、FIFO 分配或变动记录。

## 范围

仓库模块负责：

- 仓库基本信息。
- 仓库编码和名称规则。
- 仓库类型。
- 仓库状态。
- 仓库位置和联系信息。
- 仓库软删除或停用规则。

仓库模块不负责：

- SKU 定义。
- 物料主数据。
- 库存数量。
- 库存层记录。
- 预留库存。
- 可用库存计算。
- 库存变动记录。
- FIFO 分配。
- 增加、预留、释放或扣减库存的操作。

## 通用字段

仓库仅包含仓库主数据字段。

示例：

- `id`
- `code`
- `name`
- `type`
- `status`
- `location`
- `contact_name`
- `contact_phone`
- `remark`
- `created_at`
- `updated_at`
- `deleted_at`

仓库不得包含库存数量字段。

仓库记录中禁止包含的字段：

- `sku_id`
- `batch_id`
- `on_hand_qty`
- `reserved_qty`
- `available_qty`

## 与库存的关系

库存将仓库作为必需的库存维度。

库存记录按以下维度跟踪：

```text
warehouse + SKU
warehouse + SKU + batch
```

规则：

- 库存变更操作必须包含 `warehouse_id`。
- 库存模块负责库存状态和库存操作规则。
- 仓库模块仅负责校验仓库是否存在，以及能否参与库存变更操作。
- 库存可以依赖仓库应用服务或稳定的仓库应用契约。
- 仓库不得直接更新库存表。
- 仓库不得计算库存数量。

## 状态规则

建议的仓库状态：

- `active`
- `inactive`

规则：

- `active` 仓库可以参与库存查询和变更操作。
- `inactive` 仓库仍可用于库存查询。
- `inactive` 仓库不得用于库存变更操作。
- 库存变更操作包括增加、预留、释放、扣减可用库存和扣减预留库存。
- 停用仓库不应改变现有库存数量或变动记录。

## 删除与停用规则

仓库应采用软删除或停用，不应硬删除。

规则：

- 如果仓库存在任何库存记录，则不得删除该仓库。
- 如果仓库存在任何库存记录，则只能停用该仓库。
- 库存记录包括仓库 + SKU 库存余额、库存层、预留或变动记录。
- 已停用的仓库仍可用于查询历史库存数据。
- 没有库存记录的仓库，可以在业务规则允许时软删除。
- 禁止硬删除被库存或变动记录引用的仓库。

检查仓库是否有库存时，不得直接访问库存仓储。

允许的方式：

- 使用库存应用服务或稳定的库存应用契约。
- 使用更高层级的应用服务协调仓库和库存检查。
- 使用数据库约束防止删除被引用的仓库。

禁止的方式：

- 仓库仓储直接查询库存表。
- 仓库服务直接使用库存仓储。
- 删除仓库后留下 `warehouse_id` 悬空的库存记录。

## 边界规则

- 库存可以将仓库作为校验依赖。
- 仓库不得依赖物料或 SKU 模块。
- 仓库不得负责库存操作逻辑。
- 其他模块不得直接访问仓库仓储。
- 跨模块校验（例如检查仓库是否存在或是否启用）必须通过仓库服务层完成。

## 分层规则

仓库模块必须遵循项目的依赖方向：

```text
处理器 -> 服务 -> 仓储
```

- 处理器解析 HTTP 输入并返回统一响应。
- 服务负责仓库业务规则和用例。
- 仓储仅负责持久化逻辑。

需要事务时，必须在服务层启动并完成事务。

## 业务规则

- `code` 必须唯一标识一个仓库。
- `name` 应便于人类阅读，不应作为唯一业务标识。
- 除非仓库操作需要更多细节，否则 `type` 应保持简单。
- `status` 控制仓库能否用于库存变更操作。
- 默认的列表或详情查询不得返回已软删除的仓库。
- 被库存记录、预留或变动记录引用的仓库不得硬删除。

## 仓库类型规则

仓库类型一开始可以保持简单。

建议的初始类型：

- `normal`
- `virtual`

未来可能包含的类型：

- 质检仓
- 次品仓
- 退货仓
- 冻结仓

在业务需要之前，不要引入仓库库位或货位层级的复杂性。

如果以后需要跟踪库位/货位，应将其建模为独立概念，例如：

```text
warehouse -> location/bin
```

## API 规则

仓库 API 必须在 `/api/v1` 下使用复数资源名称。

预期资源路径：

```text
/api/v1/warehouses
```

标准操作：

- `GET /api/v1/warehouses`：列出仓库。
- `GET /api/v1/warehouses/:id`：获取仓库详情。
- `POST /api/v1/warehouses`：创建仓库。
- `PUT /api/v1/warehouses/:id`：更新仓库。
- `DELETE /api/v1/warehouses/:id`：允许时软删除仓库。
- `PUT /api/v1/warehouses/:id/disable`：停用仓库。

库存变更 API 不得放在仓库资源下。它们属于库存模块。

所有响应必须使用 `pkg/response` 包。

## 禁止模式

- 在仓库记录中存储库存数量字段。
- 在仓库服务中更新库存。
- 在仓库服务中预留或释放库存。
- 在仓库服务中执行 FIFO 分配。
- 硬删除存在库存、预留或变动记录的仓库。
- 仅因为仓库处于停用状态就阻止库存查询。
- 允许对停用仓库执行库存变更操作。
